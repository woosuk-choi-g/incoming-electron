# Timer Overlay 포트폴리오 로드맵

## 1. 프로젝트 방향

Timer Overlay는 게임 중 반복되는 이벤트를 놓치지 않도록 여러 타이머를
화면 위에 표시하고 관리하는 Electron 데스크톱 앱이다.

포트폴리오의 핵심은 기능 개수보다 다음 문제를 설득력 있게 해결하는 데 둔다.

- 게임을 방해하지 않는 투명·항상 위 오버레이
- 여러 타이머의 정확한 상태 관리와 복구
- Electron renderer, preload, main process 사이의 안전한 IPC
- 실제 배포 가능한 설치 파일과 자동화된 품질 검증
- 이후 백엔드와 연결되는 프로필·프리셋 공유 구조

## 2. 현재 기준선

### 구현됨

- React, TypeScript, Vite 기반 renderer
- Electron main/preload 구성
- 타이머 오버레이 창 생성과 종료
- 기본 카운트다운 시작과 재설정
- 시스템 트레이 및 메인 창 복원
- 로컬 JSON 설정 저장을 위한 IPC 기반
- Electron Playwright E2E 테스트 골격

### 보완 필요

- 타이머 생성 폼과 편집 기능이 없고 샘플 값에 의존함
- 생성 시 전달한 제목과 시간이 오버레이 화면에 반영되지 않음
- 설정 저장 API가 UI와 연결되지 않았으며 IPC 입력 검증이 부족함
- 다중 창 사이의 상태 동기화 및 앱 재실행 후 복구가 없음
- UI가 Vite 초기 스타일에 가까워 제품 정체성과 반응형 설계가 부족함
- README의 기술 스택과 구현 기능 일부가 실제 코드와 일치하지 않음
- 접근성, 단위/컴포넌트 테스트, CI, 오류 처리 전략이 부족함

## 3. 단계별 로드맵

기간은 주당 10~15시간을 투입하는 개인 프로젝트를 기준으로 한 권장치다.

### Phase 0 — 제품 정의와 기준선 정리 (2~3일)

목표: 구현 범위를 고정하고 이후 변경을 측정할 수 있는 상태를 만든다.

- 핵심 사용자 시나리오 3개 정의
  - 타이머를 만들고 오버레이로 실행한다.
  - 게임 중 시작, 일시정지, 재시작, 초기화를 수행한다.
  - 앱을 다시 실행해도 프리셋과 창 위치가 복구된다.
- 타이머 도메인 모델 정의: `TimerPreset`, `TimerSession`, `TimerState`
- README를 실제 구현 상태와 일치시키고 스크린샷 영역 추가
- lint, build, 기존 E2E를 통과하는 기준 커밋 확보
- GitHub Issues 또는 프로젝트 보드에 이후 Phase를 이슈 단위로 등록

완료 기준:

- 범위에 포함할 기능과 제외할 기능이 문서화되어 있다.
- `npm run lint`, `npm run build`, `npm run test:e2e`가 통과한다.

### Phase 1 — 타이머 코어 완성 (1주)

목표: 샘플이 아닌 실제로 사용할 수 있는 타이머를 만든다.

- 제목, 시간, 반복 여부, 알림음을 입력하는 생성/편집 폼
- 시작, 일시정지, 재개, 초기화, 즉시 종료 상태 전이
- 1회성 및 반복 타이머 지원
- 시스템 시간 기준 계산으로 renderer 지연 후에도 정확도 유지
- 0 이하 표시, 중복 완료 이벤트, 빠른 연속 클릭 등 경계 조건 처리
- 타이머 로직을 UI에서 분리하고 단위 테스트 추가
- main process가 전달받은 제목과 시간을 실제 오버레이에 반영

완료 기준:

- 생성부터 완료까지 핵심 흐름을 E2E 테스트로 검증한다.
- 백그라운드 전환이나 창 이동 후에도 표시 오차가 허용 범위 내에 있다.

### Phase 2 — 오버레이 UX와 커스터마이징 (1~2주)

목표: 이 프로젝트만의 시각적 완성도와 데스크톱 경험을 만든다.

- 대시보드 정보 구조 재설계: 목록, 상태, 빠른 실행, 편집
- 오버레이 테마, 색상, 글꼴 크기, 투명도, 크기 설정
- 드래그 이동, 위치 잠금, 클릭 스루 전환
- 다중 모니터와 DPI 배율에 맞춘 위치 보정
- 완료 시 소리/시각 알림 및 음소거
- 키보드 탐색, 포커스 표시, 명도 대비 등 접근성 보완
- 빈 상태, 오류 상태, 확인 다이얼로그와 토스트 피드백

완료 기준:

- 320px 수준의 작은 창부터 일반 데스크톱 창까지 레이아웃이 깨지지 않는다.
- 창 위치와 스타일이 재실행 후 복구된다.
- 주요 화면의 before/after 이미지나 짧은 데모 영상을 확보한다.

### Phase 3 — 로컬 우선 데이터와 안정성 (1주)

목표: 백엔드 없이도 완결된 MVP를 만든다.

- 저장 계층 인터페이스를 만들고 JSON 또는 SQLite 구현을 분리
- 프리셋 CRUD, 정렬, 복제, 즐겨찾기
- 실행 중 세션 복구 정책 정의 및 구현
- IPC 요청을 스키마로 검증하고 허용 채널을 최소화
- 외부 URL 허용 목록, navigation/window open 차단 등 Electron 보안 강화
- 오류 로깅과 사용자 친화적 복구 안내
- 타이머 수 증가에 따른 CPU와 메모리 기준 측정

완료 기준:

- 비정상 종료 후에도 저장 데이터가 손상되지 않는다.
- renderer가 임의 값이나 잘못된 채널로 main process 기능을 실행할 수 없다.
- 5~10개 타이머 동시 실행 성능을 측정한 표가 문서에 있다.

### Phase 4 — 테스트, CI, 배포 (1주)

목표: 채용 담당자가 직접 설치하고 품질을 확인할 수 있게 한다.

- 핵심 상태 로직 단위 테스트와 주요 컴포넌트 테스트
- 생성, 편집, 실행, 복구, 제거, 트레이 흐름 E2E 보강
- GitHub Actions에서 lint, typecheck, test, build 자동 실행
- Windows 설치 파일 생성과 버전 메타데이터/아이콘 정리
- 릴리스 노트와 알려진 제한 사항 작성
- 최소 1대의 별도 Windows 환경에서 설치/제거 스모크 테스트

완료 기준:

- CI가 모든 PR에서 재현 가능하게 통과한다.
- GitHub Release에서 설치 파일과 변경 내역을 받을 수 있다.

### Phase 5 — 포트폴리오 패키징 (3~5일)

목표: 결과뿐 아니라 문제 해결 과정을 짧고 명확하게 보여준다.

- README 상단에 한 문장 소개, GIF, 다운로드 링크 배치
- 아키텍처 다이어그램: renderer → preload → IPC → main/storage
- 대표 기술 의사결정 2~3개 기록
  - 다중 `BrowserWindow` 선택과 성능 트레이드오프
  - 시간 차 기반 카운트다운으로 드리프트를 줄인 이유
  - context isolation과 좁은 preload API 설계
- 성능 측정 전후 수치와 테스트 전략 공개
- 회고: 실패한 접근, 한계, 다음 단계

완료 기준:

- 처음 보는 사람이 3분 안에 문제, 핵심 기능, 기술적 난점, 실행법을 이해한다.
- 60~90초 데모 영상과 설치 가능한 릴리스가 있다.

## 4. 프론트엔드 MVP 종료선

아래 항목이 충족되면 프론트엔드 1차 완성으로 보고 백엔드를 시작한다.

- 사용자가 프리셋을 생성, 수정, 삭제, 실행할 수 있다.
- 타이머가 시작, 일시정지, 재개, 초기화, 반복된다.
- 여러 오버레이가 독립적으로 동작하고 위치/스타일이 저장된다.
- 앱 재실행 후 프리셋과 필요한 세션 상태가 복구된다.
- 접근 가능한 대시보드와 일관된 디자인 시스템이 적용된다.
- 핵심 사용자 여정 E2E와 상태 로직 단위 테스트가 통과한다.
- Windows 설치 파일, README, 데모 영상이 준비되어 있다.

커뮤니티 피드, 채팅, 모바일 앱, 네이티브 DirectComposition 렌더러는 MVP에서
제외한다. 이 기능들은 핵심 가치 검증보다 범위와 운영 복잡도를 크게 늘린다.

## 5. 백엔드 확장 로드맵

### Backend Phase 1 — 인증과 동기화 (1~2주)

- 이메일 또는 OAuth 로그인
- 사용자별 타이머 프리셋 API
- 로컬 우선 동작과 서버 동기화
- `updatedAt` 또는 버전 기반 충돌 처리
- API 계약과 오류 응답 표준화

### Backend Phase 2 — 공유 프리셋 (1~2주)

- 공개/비공개 프리셋, 공유 링크
- 태그, 검색, 즐겨찾기, 복제
- 소유권과 수정 권한 검증
- 페이지네이션 및 기본 rate limit

### Backend Phase 3 — 세션 통계 (1주)

- 타이머 실행/완료 이벤트 수집
- 기간별 사용 통계와 완료율
- 데이터 보존 및 삭제 정책
- 대시보드 차트와 내보내기

백엔드 포트폴리오에서는 API 개수보다 인증/인가, 동시성, 동기화 충돌,
관측 가능성, 테스트 및 배포 과정을 주요 평가 포인트로 삼는다.

## 6. 권장 우선순위

1. 타이머 정확도와 상태 모델
2. 실제 생성/편집 흐름
3. 오버레이 조작과 설정 복구
4. IPC 보안과 오류 처리
5. 테스트·CI·설치 배포
6. 시각적 polish와 포트폴리오 문서
7. 로그인·동기화·공유 백엔드

새 기능을 추가할 때마다 최소한 정상 흐름 1개와 실패/경계 흐름 1개를
테스트하고, README의 구현 상태도 함께 갱신한다.
