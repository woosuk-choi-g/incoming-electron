# Timer Overlay 제품 및 운영 전략

_최종 업데이트: 2026-08-29_

## 현재 판단

현재의 범용 게임 타이머 오버레이만으로는 독립적인 유료 제품이 되기 어렵다.
단순 타이머는 대체재가 많고, 사용자가 지속적으로 비용을 지불할 차별점이 아직
검증되지 않았기 때문이다.

초기에는 오픈소스 무료 앱으로 공개하고 후원만 열어둔다. 실제 사용자와 반복
사용 사례를 확보한 뒤, 게임별 자동화나 협업 기능에 수요가 확인될 때 사업화를
검토한다.

## 사업 기회와 제약

### 기회

- 게임을 벗어나지 않고 반복 이벤트를 확인하려는 수요가 있다.
- 게임별 이벤트, 프리셋, 통계와 결합하면 단순 타이머보다 높은 가치를 제공할
  수 있다.
- 스트리머, 레이드 파티, 길드처럼 설정을 공유하는 사용자는 동기화와 협업
  기능에서 추가 가치를 얻을 수 있다.
- Porofessor처럼 게임 데이터와 타이머를 결합한 오버레이는 대규모 사용자를
  확보하고 광고와 구독을 운영한 사례가 있다.

### 제약

- 범용 타이머는 대체재가 많고 지불 의사가 낮을 가능성이 크다.
- 오버레이는 성능, 다중 모니터, DPI, 안티치트와 게임별 정책을 지속적으로
  관리해야 한다.
- Windows 설치 앱은 코드 서명, 배포, 자동 업데이트와 사용자 신뢰 확보에
  비용이 든다.
- 게임 이벤트 자동화는 게임사 또는 플랫폼 API 변화에 영향을 받는다.

## 1단계 — 오픈소스와 후원

- 핵심 앱과 프리셋 형식을 무료로 공개한다.
- GitHub Sponsors 등 자발적 후원 창구를 제공한다.
- 설치 파일, 변경 내역, 알려진 제한 사항을 투명하게 공개한다.
- 사용 게임, 반복 사용 시나리오, 요청 기능을 이슈로 수집한다.
- 사용 통계를 수집한다면 명시적인 opt-in과 삭제 방법을 제공한다.

GitHub Sponsors는 개인 계정에서 제공하는 후원에 플랫폼 수수료를 부과하지
않는다. 후원 금액 자체보다 반복 사용자와 기여자가 생기는지를 제품 수요의
신호로 사용한다.

## 사업화 검토 신호

다음 신호가 반복해서 관찰될 때 유료화를 검토한다.

- 특정 게임에 사용자와 기능 요청이 집중된다.
- 동일 사용자가 여러 주에 걸쳐 계속 사용한다.
- 게임 이벤트 자동 감지 요청이 반복된다.
- 프리셋을 다른 사용자나 팀과 공유하려는 수요가 있다.
- 스트리머, 파티 또는 길드가 공동 설정을 요구한다.
- 사용자가 동기화·자동화·고급 설정에 대한 지불 의사를 직접 표현한다.

다운로드 수만으로 유료화를 결정하지 않는다. 유지율, 반복 사용, 지원 부담,
지불 의사를 함께 확인한다.

## 2단계 — 선택적 유료 서비스

핵심 타이머와 로컬 저장은 무료로 유지한다. 운영 비용이나 지속적인 콘텐츠
관리가 필요한 편의 기능을 유료 후보로 둔다.

- 클라우드 동기화와 백업
- 팀·길드 프리셋 공유
- 게임별 자동 이벤트 감지
- 고급 테마와 스트리밍 연동
- 다중 장치와 프로필 관리
- 큐레이션된 게임별 프리셋

유료 기능이 핵심 로컬 사용을 제한하거나 오버레이에 방해되는 광고를 강제하지
않도록 한다.

## 3단계 — Overwolf 검토

Overwolf는 앱 유통, 게임 호환 계층, 광고와 구독 수익화를 제공한다. 반면
수익화 앱은 Overwolf의 광고 또는 구독 체계를 사용해야 하며 플랫폼 정책과
수익 배분 조건을 따라야 한다.

다음 조건을 충족할 때 통합을 검토한다.

- 독립 Electron 앱에서 반복 사용 수요가 확인됐다.
- 특정 게임의 공식 이벤트 API가 제품 가치에 필수적이다.
- Overwolf 유통으로 얻는 사용자 접근성이 플랫폼 의존 비용보다 크다.
- 독립판과 Overwolf판을 함께 유지할 범위와 책임이 정의됐다.

초기부터 플랫폼에 종속하지 않고, 독립판으로 가치를 검증한 다음 통합 여부를
결정한다.

## 유료화와 코드 저장소

앱을 유료화하는 것과 GitHub 저장소를 비공개로 전환하는 것은 별개의 결정이다.
유료 앱도 공개 저장소로 운영할 수 있으며, 핵심 앱을 공개한 채 클라우드 동기화,
관리형 서비스, 공식 빌드와 코드 서명, 지원을 유료 가치로 제공할 수 있다.

현재 저장소에는 `LICENSE` 파일이 없다. 따라서 코드를 공개하고 있다는 사실만으로
오픈소스 사용 권한이 부여되지는 않는다. 오픈소스 코어 전략을 확정하기 전에 다음을
결정한다.

- 상업적 포크를 허용하는 허용적 라이선스를 쓸지
- 수정본 공개 의무가 있는 카피레프트 라이선스를 쓸지
- 상표, 공식 배포판 이름과 코드 서명 인증서를 별도로 보호할지
- 서버 코드, 운영 자격 증명과 유료 콘텐츠를 별도 비공개 저장소로 분리할지

공개 저장소를 유지하면 표준 GitHub-hosted Actions, CodeQL, secret scanning과
dependency review를 공개 저장소 무료 범위에서 계속 사용할 수 있다. 외부 기여,
이슈와 공개 로드맵도 초기 제품 신뢰와 수요 검증에 도움이 된다.

저장소를 비공개로 전환하면 다음 영향이 있다.

- GitHub Free의 비공개 저장소 Actions는 계정별 월간 포함 사용량을 소비한다.
- CodeQL code scanning을 계속 사용하려면 조직과 GitHub Code Security 라이선스가
  필요하다.
- 전체 secret scanning과 push protection을 계속 사용하려면 지원되는 조직 플랜과
  GitHub Secret Protection이 필요하다.
- dependency graph와 기본 Dependabot alerts는 계속 사용할 수 있지만 일부 고급
  Dependabot 기능은 제한될 수 있다.
- 기존 공개 포크는 비공개로 바뀌지 않고 원본에서 분리되며, 이미 복제되거나 배포된
  소스도 회수할 수 없다.
- stars와 watchers가 삭제되므로 공개 프로젝트의 발견성과 사회적 증거가 감소한다.

따라서 현재 단계에서는 코어 저장소를 공개로 유지하고 라이선스를 명시하는 방향을
우선한다. 실제 운영 비용이나 경쟁 우위가 있는 서버 기능이 생기면 이를 별도 비공개
저장소로 분리한다. 저장소 전체의 비공개 전환은 유료 기능의 비밀 유지 효과가 관련
GitHub 기능 비용과 커뮤니티 손실보다 클 때만 검토한다.

## 권장 수익 모델

기본 방향은 `오픈소스 코어 + 자발적 후원 + 선택적 유료 서비스`다.

1. MVP를 무료 오픈소스로 완성한다.
2. 후원과 커뮤니티 기여를 받을 수 있게 한다.
3. 특정 게임이나 사용자군에서 반복 수요를 찾는다.
4. 서버 비용과 지속적인 유지 관리가 필요한 기능만 유료화한다.
5. 플랫폼 통합은 검증된 수요를 확대하는 수단으로 사용한다.
